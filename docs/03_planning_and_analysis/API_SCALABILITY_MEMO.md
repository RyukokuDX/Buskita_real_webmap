# APIの仕組みとスケーラビリティに関する重要メモ

## 1. APIの二層構造について

当アプリケーションは、役割の異なる2種類のAPIで構成されている。

### 1.1. 外部API (バス会社提供)
- **役割:** リアルタイムのバス情報（位置、遅延、乗客数）を提供する、大本のデータソース。
- **エンドポイント例:** `https://api.buskita.com/get-buses`
- **特徴:**
  - アプリの外部に存在する、私たちが直接制御できないAPI。
  - 不定期に応答が不安定になることがあるため、当アプリ側でバックアップ/フォールバック機能を実装済み。

### 1.2. 内部API (私たちが作成)
- **役割:** 外部APIから取得した生のデータを、Webページ（フロントエンド）で扱いやすいように加工・整形して提供する。
- **エンドポイント例:** `/api/bus_locations`, `/api/timetable_data`
- **存在意義:**
  - フロントエンドとバックエンドの処理を分離（関心を分離）し、開発の見通しを良くする。
  - 複雑なデータ取得・加工処理をバックエンドに集約することで、フロントエンドの負担を軽減する。

## 2. APIの呼び出しメカニズム (現状の設計)

- **基本原則:** オンデマンド（リクエスト駆動）
- **トリガー:** **Webブラウザからの内部API (`/api/bus_locations`) へのアクセスがトリガーとなる。**
- **連動:** 内部APIが呼び出されるたびに、バックエンドサーバー (`web_map_app.py`) が外部APIを呼び出す仕組みになっている。

**結論:** **ユーザーからのアクセスが無い限り、外部APIが呼び出されることはない。** これは、無駄な通信を発生させない効率的な設計である。

## 3. 将来的なスケーラビリティに関する課題【最重要】

現状のオンデマンド設計は、少数のユーザー利用においては効率的だが、将来的にユーザー数が増加した場合、深刻な問題を引き起こす可能性がある。

- **問題点:**
  - **100人のユーザーが同時にアクセスすると、外部APIもほぼ100回呼び出されてしまう。**
- **潜在的なリスク:**
  1.  **外部APIサーバーへの過負荷:** バス会社のサーバーに多大な負荷をかけてしまう。
  2.  **アクセスブロックのリスク:** 外部API提供者から、我々のサーバーが「攻撃」と見なされ、アクセスを遮断される危険性がある。
  3.  **パフォーマンスの低下:** サーバーの応答速度が低下し、アプリの動作が重くなる。

## 4. 解決策の方向性: 「キャッシュ」の導入

この問題を解決するため、将来的には**「キャッシュ」**の仕組みを導入する必要がある。

- **キャッシュとは:** 一度取得した情報を、サーバー内に短時間（例: 3〜5秒）だけ保存しておく技術。
- **導入後の流れ:**
  1.  最初のユーザーアクセスで外部APIを呼び出し、結果をキャッシュに保存する。
  2.  次のユーザーからは、キャッシュの有効期限が切れるまで、外部APIを呼び出さずにキャッシュから高速で応答する。
- **期待される効果:**
  - ユーザー数がどれだけ増えても、外部APIへのアクセスは「N秒に1回」という一定の頻度に抑えられる。
  - サーバー負荷の劇的な軽減と、応答速度の向上が見込める。
  

**総括:** アプリケーションの安定的な成長と運用のために、**キャッシュ機構の実装は、将来の最優先改善事項の一つ**である。
